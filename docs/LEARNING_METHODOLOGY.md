# 源码课程编写与审稿

## 从一个可以回答的问题开始

每章面向一位会写代码、第一次读这个项目的人。先写业务问题，例如“用户请求一次工具调用后，哪一段程序接收结果？”再确认该版本是否有足够的代码回答它。依次讲清系统边界、输入和输出、执行路径，最后带读者进入函数和类。首章先给架构图，后续章节标出自己位于图中的位置。

| 步骤 | 作者实际要做的事 | 评审时怎样检查 |
| --- | --- | --- |
| 选材 | 固定仓库与完整提交，从入口沿调用处、处理函数、结果消费处取证 | 审稿人在同一版本打开每个闭区间，看到相应定义或调用；证据只覆盖所需代码 |
| 解释 | 用一句普通中文讲职责，再介绍原项目术语；按先后讲参数、分支、状态流向与返回值 | 读者能说出“谁传给谁、在什么条件下”；遇到事件、异步和错误分支，要说明实际核对的范围 |
| 标注 | 每条技术断言选事实、推断、建议；把仍无依据的因果关系写入疑问 | “这段代码调用了 X”可由调用点证实；“作者可能为了 Y”说明推理过程；“在自己的实现里可用 Z”说明取舍 |
| 场景 | 给出一个具体输入和目标，带着读者依次打开证据；示例输入明确标为教学场景 | 讲解里的每个源码步骤都能回到同一版；模拟事件单独标注 |
| 练习 | 先让读者预测下一步，再定位行号并解释原因；给出答案、依据和错因 | 至少一道题能通过阅读指定证据作答；追踪题有可逐项核对的评分点 |
| 复习 | 用简短语言概括机制，给出一次可重复的阅读路线 | 学习者隔天从总结回到函数，能自己复述这条流程 |

## 十二项成稿清单

按顺序填写学习目标、前置知识、概念、源码位置、关键函数或类、执行流程、调用关系、业务场景、设计原因、常见问题、练习与总结。每项的可保存字段见[课程契约](LEARNING_SCHEMA.md)。章节可以短，不能靠空数组或泛泛的“自行阅读源码”交付。

## 教学边界

- 技术事实必须引用公开可核验的源码。精确行号只对指定提交有效；若解释跨越多处调用，引用两端或所需的完整证据链。
- 中文讲解保留原始路径、函数名、事件名和类型名。引用合适长度的材料，优先定位原文；注意上游许可。
- “已实现”“公开接口承诺”“教学模拟”“作者推断”在界面和讲义上应可区分。缺少证据时缩小结论或登记待查问题。
- 单项目课程内只讲该项目该版。跨项目联系进入 P6 比较材料，各列有各自的来源。Claude Code 的公开仓库、官方 SDK 和内部实现边界见[来源规范](REPOSITORY_SOURCES.md)。
- 一章的发布条件是结构验证、证据复核、独立阅读回放及练习验答全部通过。保留未通过项，修改后发布新内容版次。
